## 2. DAX concepts used in this layer (read first)
**Measure vs calculated column.** A calculated column is computed once per row when the data loads and stored. A measure is computed when a visual asks for it, for exactly the cells in that visual. Totals and ratios belong in measures, because they must change with filters.

**Filter context.** The set of filters active when a measure is evaluated: slicers, the row and column of a matrix cell, the bar of a chart, page and report filters. [Revenue] in the 'West' bar is evaluated with the filter region = West. Measures never need to 'know' which visual they are in.

**How filters travel.** Filters flow from a dimension to the fact table along the one-to-many relationships (dim_location -> fct_sales). Because all relationships are single-direction, a filter on fct_sales does not filter the dimensions back; this keeps results predictable.

**CALCULATE.** CALCULATE ( expression, filter, ... ) evaluates the expression after changing the filter context: adding a filter (dim_customer[is_excluded_from_customer_analysis] = 0), replacing dates (SAMEPERIODLASTYEAR), or removing filters (REMOVEFILTERS, ALLSELECTED).

**Row context and context transition.** Iterators such as SUMX and FILTER walk a table row by row. When a measure like [Profit] is used inside them, Power BI turns the current row into a filter (context transition). FILTER ( VALUES ( fct_sales[product_key] ), [Profit] < 0 ) therefore evaluates each product's own profit.

**ALL, REMOVEFILTERS and ALLSELECTED.** REMOVEFILTERS ( table ) ignores filters on that table (used for the portfolio hurdle). ALLSELECTED () keeps the user's slicer choices but ignores the grouping of the visual (used for 'share of total').

**BLANK.** BLANK means 'no value'. DIVIDE returns BLANK for an empty or zero denominator, and visuals hide blank cells. That is why growth measures return BLANK, not 0, when no comparison exists: 0% would be a false statement.

**Time intelligence prerequisites.** A continuous date table (every day, full years), marked as the date table, with an active relationship to the fact table. dim_date meets all three.

**Model rules these measures rely on:** star schema with single-direction relationships; `dim_date` marked as the date table; report-level filter `fct_sales[is_core_scope] = 1`; all `*_key` columns hidden so users build visuals from measures and dimension attributes only.

## 3. Core measures in detail
Expected values are computed independently from the SQL warehouse (core scope). Section 6 explains how to compare.

### 3.1 Revenue
```dax
Revenue =
SUM ( fct_sales[sales] )
```
*Format:* `#,0`

**1. What it does.** Adds up the `sales` column of every order line that survives the current filters. If the page is filtered to West and 2025, it adds only West lines from 2025. `sales` is already after discount, so this is net revenue.

**2. Where to use it.** Every page: KPI card (page 1, 2), trends, category and region visuals, and as the base of almost every ratio. (In the spec: P1 Revenue; P1 Revenue trend: this year vs prior year; P1 Category performance; P1 Region performance: profit (label = margin)….)

**3. Common mistakes.**
- Building it as a calculated column on the fact table and then summing: unnecessary, slower, and it does not respond better to filters.
- Forgetting the report-level scope filter: the card would then include Canadian copies and show 2,326k instead of 2,297k.
- Calling it 'gross sales': the source value is net of discount; gross (list) value is a separate measure.

**4. How to validate it.**
```sql
SELECT SUM(sales) FROM fct_sales WHERE is_core_scope = 1;
```
Expected: All years: **2,296,919**, 2023: **483,966**, 2024: **470,533**, 2025: **609,206**, 2026: **733,215**.

### 3.2 Profit
```dax
Profit =
SUM ( fct_sales[profit] )
```
*Format:* `#,0`

**1. What it does.** Adds up the `profit` column for the lines in the current filter context. Profit can be negative on individual lines, so the total already nets losses against gains.

**2. Where to use it.** KPI cards (pages 1 and 3), profit trend, sub-category and region bars, and every margin calculation. (In the spec: P1 Profit; P1 Profit trend by month; P1 Category performance; P1 Region performance: profit (label = margin)….)

**3. Common mistakes.**
- Filtering out loss-making lines 'to clean the data': losses are real business results.
- Comparing it to 'gross profit': the dataset does not say which costs profit is net of.

**4. How to validate it.**
```sql
SELECT SUM(profit) FROM fct_sales WHERE is_core_scope = 1;
```
Expected: All years: **286,409**, 2023: **49,556**, 2024: **61,619**, 2025: **81,795**, 2026: **93,439**.

### 3.3 Profit Margin %
```dax
Profit Margin % =
DIVIDE ( [Profit], [Revenue] )
```
*Format:* `0.0%`  ·  *Depends on:* `Revenue`, `Profit`

**1. What it does.** Divides total profit by total revenue for whatever is in the current filter context. Because both totals are recalculated for each cell of a visual, the margin of 'Furniture in the West' is that group's own profit divided by its own revenue.

**2. Where to use it.** KPI card (pages 1 and 3), category matrix, region labels, scatter Y-axis, heat maps. (In the spec: P1 Profit margin; P1 Category performance; P1 Region performance: profit (label = margin); P3 Profit margin….)

**3. Common mistakes.**
- Averaging line margins (AVERAGE of profit/sales): a 2-dollar line would count as much as a 2,000-dollar line. In this data that gives 12.0% instead of the correct 12.5%.
- Using '/' instead of DIVIDE: a cell with no revenue then shows an error instead of staying blank.
- Storing margin as a calculated column and summing or averaging it in visuals.

**4. How to validate it.**
```sql
SELECT SUM(profit) * 1.0 / SUM(sales) FROM fct_sales WHERE is_core_scope = 1;
```
Expected: All years: **12.47%**, 2023: **10.24%**, 2024: **13.10%**, 2025: **13.43%**, 2026: **12.74%**.

### 3.4 Orders
```dax
Orders =
DISTINCTCOUNT ( fct_sales[order_id] )
```
*Format:* `#,0`

**1. What it does.** Counts how many different order IDs appear in the filtered lines. The table has one row per order line, and an order usually has two or more lines, so counting rows would overstate orders.

**2. Where to use it.** KPI cards (pages 1 and 2), the denominator of Average Order Value and Profit per Order, growth drivers on page 2. (In the spec: P1 Orders; P2 Orders; P4 Customer profitability: revenue vs margin.)

**3. Common mistakes.**
- Using COUNTROWS(fct_sales) or COUNT(order_id): that counts lines (9,993), not orders (5,009).
- Summing orders across categories: one order can contain several categories, so category order counts add up to more than the total. That is correct behaviour, not an error.

**4. How to validate it.**
```sql
SELECT COUNT(DISTINCT order_id) FROM fct_sales WHERE is_core_scope = 1;
```
Expected: All years: **5,009**, 2023: **969**, 2024: **1,038**, 2025: **1,315**, 2026: **1,687**.

### 3.5 Customers
```dax
Customers =
DISTINCTCOUNT ( fct_sales[customer_key] )
```
*Format:* `#,0`

**1. What it does.** Counts the different customers who have at least one order line in the current filters. In a year column it means customers active that year.

**2. Where to use it.** KPI card (page 1) and the base of Valid Customers. (In the spec: P1 Customers.)

**3. Common mistakes.**
- Counting rows of dim_customer: that counts every customer in the list (804), including those with no sales in the current filter.
- Expecting regional customer counts to add up to the total: customers order from several states and regions.

**4. How to validate it.**
```sql
SELECT COUNT(DISTINCT customer_key) FROM fct_sales WHERE is_core_scope = 1;
```
Expected: All years: **793**, 2023: **595**, 2024: **573**, 2025: **638**, 2026: **693**.

### 3.6 Valid Customers
```dax
Valid Customers =
CALCULATE ( [Customers], dim_customer[is_excluded_from_customer_analysis] = 0 )
```
*Format:* `#,0`  ·  *Depends on:* `Customers`

**1. What it does.** The same distinct count, but CALCULATE first adds a filter that keeps only customers not flagged in the data-quality audit (the placeholder 'Sample Company A' and the identity-anomaly records).

**2. Where to use it.** Customer KPIs on page 4 and the denominator of Profit per Customer and Revenue per Customer. (In the spec: P4 Valid customers; P4 Customer segments by business segment.)

**3. Common mistakes.**
- Using Customers in per-customer ratios while the numerator uses all customers' profit: numerator and denominator must describe the same population.

**4. How to validate it.**

### 3.8 Average Order Value
```dax
Average Order Value =
DIVIDE ( [Revenue], [Orders] )
```
*Format:* `#,0.00`  ·  *Depends on:* `Revenue`, `Orders`

**1. What it does.** Revenue divided by the number of distinct orders: how much a typical order is worth in the current filter context.

**2. Where to use it.** KPI cards (pages 1 and 2) and the growth-drivers visual (orders vs order value). (In the spec: P1 Average order value; P2 Average order value.)

**3. Common mistakes.**
- Averaging the sales column (AVERAGE(fct_sales[sales])): that is the average line value (230), not the average order value (459).
- Under a category filter, reading it as the full basket value: it is the revenue of that category per order that contains it.
- Treating it as typical: a few large orders pull the mean up; the median order is far smaller (Phase 4).

**4. How to validate it.**
```sql
SELECT SUM(sales) * 1.0 / COUNT(DISTINCT order_id) FROM fct_sales WHERE is_core_scope = 1;
```
Expected: All years: **458.56**, 2023: **499.45**, 2024: **453.31**, 2025: **463.27**, 2026: **434.63**.

### 3.9 Effective Discount %
```dax
Effective Discount % =
DIVIDE ( [Discount Amount], [Gross Sales] )
```
*Format:* `0.0%`  ·  *Depends on:* `Gross Sales`, `Discount Amount`

**1. What it does.** Total discount given away divided by total list value. It answers 'what share of the list price did we give up?' and weights each line by its size.

**2. Where to use it.** Page 5 KPI card, region tooltip (page 1), product tables (pages 3 and 4). (In the spec: P1 Region performance: profit (label = margin); P3 Product portfolio: revenue vs margin; P3 Products with the largest losses; P4 Products: top by profit / margin leaks….)

**3. Common mistakes.**
- Using AVERAGE(discount_rate) as 'the' average discount: it ignores line size (15.6% vs the effective 19.8%).
- Dividing discount amount by revenue instead of by list value: revenue is already reduced by the discount, which inflates the rate.

**4. How to validate it.**
```sql
SELECT SUM(discount_amount) * 1.0 / SUM(gross_sales) FROM fct_sales WHERE is_core_scope = 1;
```
Expected: All years: **19.79%**, 2023: **22.17%**, 2024: **18.80%**, 2025: **18.43%**, 2026: **19.91%**.

**2. Where to use it.** Only as the comparison label under the Effective Discount card on page 5, so readers can see why the two differ. (In the spec: P5 Effective discount.)

### 3.11 Last Sales Date Key
```dax
Last Sales Date Key =
CALCULATE ( MAX ( fct_sales[order_date_key] ), REMOVEFILTERS () )
```
*Format:* `0`

**1. What it does.** Finds the latest order date in the whole dataset (REMOVEFILTERS ignores all slicers). It is a helper that stops time-intelligence measures from inventing values for dates after the data ends.

**2. Where to use it.** Hidden. Used inside PY Comparison Valid and the rolling 12-month measures.

**3. Common mistakes.**
- Without it, the date table (which runs to the end of 2027 for ship dates) lets 'prior year' and rolling measures show values for 2027 months that have no sales, so a dashed prior-year line runs on past the real data.

**4. How to validate it.**
```sql
SELECT MAX(order_date_key) FROM fct_sales;
```

### 3.12 PY Comparison Valid
```dax
PY Comparison Valid =
HASONEVALUE ( dim_date[year] )
    && MIN ( dim_date[date_key] ) <= [Last Sales Date Key]
```
*Format:* `True/False`  ·  *Depends on:* `Last Sales Date Key`

**1. What it does.** Returns TRUE only when exactly one year is in the current filter context (HASONEVALUE) and that period does not start after the data ends. A month in a chart, a single selected year, or a row of a year matrix all qualify; 'all years' does not.

**2. Where to use it.** Hidden. Every prior-year measure starts with IF ( [PY Comparison Valid], ... ).

**3. Common mistakes.**
- Leaving it out: with all four years selected, SAMEPERIODLASTYEAR shifts the range back one year, finds the same sales inside the date table, and reports growth of 0%. That number looks plausible and is meaningless.
- Replacing it with ISFILTERED(dim_date[year]): a month on a chart axis is not a year filter, so monthly growth would disappear.

**4. How to validate it.**
```sql
-- no SQL equivalent: it controls when a comparison is defined
```

### 3.13 Revenue PY
```dax
Revenue PY =
IF ( [PY Comparison Valid], CALCULATE ( [Revenue], SAMEPERIODLASTYEAR ( dim_date[date] ) ) )
```
*Format:* `#,0`  ·  *Depends on:* `Revenue`, `PY Comparison Valid`

**1. What it does.** Revenue for the same dates one year earlier. SAMEPERIODLASTYEAR takes the dates currently in the filter (for example March 2025) and shifts them back a year (March 2024); CALCULATE then evaluates Revenue for those dates.

**2. Where to use it.** Dashed comparison line on the page 1 revenue trend; comparison label on page 2; input to Revenue Growth %. (In the spec: P1 Revenue trend: this year vs prior year; P2 Revenue growth vs prior year; P2 Monthly growth vs same month last year.)

**3. Common mistakes.**
- Not marking dim_date as a date table: time-intelligence functions may then return wrong or blank results.
- Using the date column from the fact table instead of dim_date[date]: time intelligence needs the continuous date table.

**4. How to validate it.**
```sql
SELECT SUM(sales) FROM fct_sales WHERE is_core_scope = 1 AND order_date_key BETWEEN 20250101 AND 20251231;  -- prior year of 2026
```
Expected: All years: **(blank)**, 2023: **(blank)**, 2024: **483,966**, 2025: **470,533**, 2026: **609,206**.

### 3.14 Revenue Growth %
```dax
Revenue Growth % =
VAR _cy = [Revenue]
VAR _py = [Revenue PY]
RETURN
    IF ( NOT ISBLANK ( _cy ) && _py > 0, DIVIDE ( _cy - _py, _py ) )
```
*Format:* `0.0%`  ·  *Depends on:* `Revenue`, `Revenue PY`

**1. What it does.** (Revenue this period - revenue same period last year) / revenue same period last year. VAR stores each value once so the formula is readable and each value is calculated only once. The IF returns BLANK when there is nothing to compare.

**2. Where to use it.** Sales growth and YoY sales growth everywhere: page 1 card label, page 2 card, monthly growth chart, growth drivers, breakdown labels. (In the spec: P1 Revenue trend: this year vs prior year; P1 Category performance; P2 Revenue growth vs prior year; P2 Monthly growth vs same month last year….)

**3. Common mistakes.**
- Computing month-on-month growth and calling it growth: in this seasonal business it mostly measures the calendar (Phase 4).
- Showing a growth figure for 'all years' (prevented by PY Comparison Valid).
- Writing (CY - PY) / CY: the base must be the prior year.

**4. How to validate it.**
```sql
SELECT (SUM(CASE WHEN order_date_key >= 20260101 THEN sales END) * 1.0 / SUM(CASE WHEN order_date_key BETWEEN 20250101 AND 20251231 THEN sales END)) - 1 FROM fct_sales WHERE is_core_scope = 1;
```
Expected: All years: **(blank)**, 2023: **(blank)**, 2024: **-2.78%**, 2025: **29.47%**, 2026: **20.36%**.

### 3.16 Profit Growth %
```dax
Profit Growth % =
VAR _cy = [Profit]
VAR _py = [Profit PY]
RETURN
    IF ( NOT ISBLANK ( _cy ) && _py > 0, DIVIDE ( _cy - _py, _py ) )
```
*Format:* `0.0%`  ·  *Depends on:* `Profit`, `Profit PY`

**1. What it does.** The same calculation for profit, with one extra rule: it returns BLANK when last year's profit was zero or negative. Growth from a negative base has a misleading sign (going from -10k to +5k would show -150%). Profit Change shows the absolute difference instead.

**2. Where to use it.** Profit YoY label on pages 1 and 3.

**3. Common mistakes.**
- Allowing a negative base: a loss shrinking to a smaller loss can show as large negative 'growth'.
- Comparing profit growth with revenue growth without looking at margin change (use Margin Change pp).

**4. How to validate it.**
```sql
SELECT (SUM(CASE WHEN order_date_key >= 20260101 THEN profit END) * 1.0 / SUM(CASE WHEN order_date_key BETWEEN 20250101 AND 20251231 THEN profit END)) - 1 FROM fct_sales WHERE is_core_scope = 1;
```
Expected: All years: **(blank)**, 2023: **(blank)**, 2024: **24.34%**, 2025: **32.74%**, 2026: **14.24%**.

### 3.17 Margin Change pp
```dax
Margin Change pp =
VAR _py = [Profit Margin % PY]
RETURN
    IF ( NOT ISBLANK ( _py ) && NOT ISBLANK ( [Revenue] ), [Profit Margin %] - _py )
```
*Format:* `+0.0%;-0.0%`  ·  *Depends on:* `Revenue`, `Profit Margin %`, `Profit Margin % PY`

**1. What it does.** This period's margin minus the prior period's margin, in percentage points. A move from 13.4% to 12.7% is -0.7 points, not '-5%'.

**2. Where to use it.** Margin card label on pages 1 and 3.

**3. Common mistakes.**
- Expressing a change in margin as a % growth of the margin: it confuses readers and exaggerates small changes.

**4. How to validate it.**

Expected: All years: **(blank)**, 2023: **(blank)**, 2024: **+2.86 pp**, 2025: **+0.33 pp**, 2026: **-0.68 pp**.

### 3.19 Profit per Customer
```dax
Profit per Customer =
DIVIDE (
    CALCULATE ( [Profit], dim_customer[is_excluded_from_customer_analysis] = 0 ),
    [Valid Customers]
)
```
*Format:* `#,0.00`  ·  *Depends on:* `Profit`, `Valid Customers`

**1. What it does.** Profit earned from valid customers divided by the number of valid customers. CALCULATE applies the same customer filter to the numerator that Valid Customers applies to the denominator, so both describe the same group.

**2. Where to use it.** Page 4 KPI card. (In the spec: P4 Profit per customer.)

**3. Common mistakes.**
- Dividing [Profit] (all customers) by [Valid Customers]: the placeholder customer's profit would be divided among the others.
- Averaging a customer-level profit column: unnecessary, and it breaks when filters change.

**4. How to validate it.**
```sql

```
Expected: All years: **360.35**, 2023: **82.14**, 2024: **107.71**, 2025: **128.18**, 2026: **134.90**.

Three supporting measures deserve a closer look because they iterate:

**Loss-making Products**
```dax
Loss-making Products =
COUNTROWS ( FILTER ( VALUES ( fct_sales[product_key] ), [Profit] < 0 ) )
```
FILTER walks the list of products in context (VALUES), evaluates [Profit] for each one through context transition, and keeps those below zero. Iterating over fct_sales rows instead would test each line, not each product.

**Top 10% Customer Profit Share**
```dax
Top 10% Customer Profit Share =
VAR _cust = CALCULATETABLE ( VALUES ( fct_sales[customer_key] ),
                             dim_customer[is_excluded_from_customer_analysis] = 0 )
VAR _n = ROUNDUP ( COUNTROWS ( _cust ) * 0.1, 0 )
VAR _top = TOPN ( _n, _cust, [Profit], DESC )
RETURN
    DIVIDE ( SUMX ( _top, [Profit] ), SUMX ( _cust, [Profit] ) )
```
Builds the list of valid customers in context, takes the top 10% by profit with TOPN, and divides their profit by all valid customers' profit. It recalculates for any slicer, so it answers 'top 10% of which customers?' correctly.

**Loss-making Rules**
```dax
Loss-making Rules =
VAR _cells = SUMMARIZE ( fct_sales, dim_location[state_province], dim_product[sub_category] )
RETURN
    COUNTROWS ( FILTER ( _cells, [Profit] < 0 ) )
```
SUMMARIZE creates every state x sub-category combination present in the fact table (one discount rule each); FILTER keeps the combinations with negative profit.

## 5. Considered but not created
**Period-over-period growth (vs the previous month or quarter).** In a strongly seasonal business it mostly measures the calendar: November vs October looks like growth every year. 'Sales Growth' and 'YoY Sales Growth' are therefore the same measure here.
```dax
Revenue Prev Period =
VAR _first = MIN ( dim_date[date] )
VAR _days = MAX ( dim_date[date] ) - _first + 1
RETURN
    CALCULATE ( [Revenue], DATESBETWEEN ( dim_date[date], _first - _days, _first - 1 ) )
```

**Year-to-date measures.** Every dataset year is complete, so YTD equals the yearly total. Kept in dax_optional_measures.dax.

**Return and shipping measures.** Not part of the profitability question; returns are recorded per order only. Kept in the optional file.

**Margin as a calculated column.** A stored ratio cannot be re-aggregated correctly; a measure recalculates it for every filter.

**Separate 'YoY' copies of each growth measure.** Duplicates of the same logic would drift apart; one measure per concept.
