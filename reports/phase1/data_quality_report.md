## 4. Issues, interpretation and decisions
### DQ01 — Near-duplicate order lines (identical except Row ID)
- **Severity:** Medium | **Decision:** CORRECT | **Rows in issue log:** 2
- **Evidence:** copies: row 392 (US-2023-150119), row 1700 (CA-2023-153623)
- **What it means:** Two rows describe the same order, product, quantity, discount, sales and profit. Only the technical Row ID differs, which suggests the line was loaded twice.
- **Why this decision:** Keeping a double-loaded line overstates sales, profit and units. A genuine split line would normally differ in quantity or value; these do not differ at all.
- **Approach:** Keep the first occurrence (lowest row_id), remove the copy, and record the removed row_id and its sales/profit in the cleaning log.

### DQ02 — Postal codes stored as numbers (leading zeros lost) and mixed types
- **Severity:** Medium | **Decision:** CORRECT | **Rows in issue log:** 438
- **Evidence:** python types in column: {'int': 9983, 'str': 211}; US codes that lost a leading zero: 438
- **What it means:** US ZIP codes such as 05401 were stored as the number 5401. Canadian codes are text (e.g. 'M7A'). The column therefore mixes numbers and strings.
- **Why this decision:** A postal code is an identifier, not a quantity. Numeric storage breaks joins, map visuals and any lookup against external geography data.
- **Approach:** Convert to text. Zero-pad US codes to 5 digits. Keep Canadian codes as given (upper-case, trimmed).

### DQ03 — Customer IDs with inconsistent letter casing
- **Severity:** Low | **Decision:** CORRECT | **Rows in issue log:** 43
- **Evidence:** examples: ['Co-12640', 'Dl-13600', 'Dp-13240']
- **What it means:** Some IDs use a lower-case second letter (e.g. 'Dl-13600') while the standard format is two upper-case letters plus five digits.
- **Why this decision:** Case differences can split one customer into two keys in SQL or Power BI joins. We verified that upper-casing creates no collision with another customer.
- **Approach:** Upper-case all customer IDs, then re-validate the ID pattern.

### DQ04 — Customer names with inconsistent casing / formatting
- **Severity:** Low | **Decision:** CORRECT | **Rows in issue log:** 35
- **Evidence:** examples: ['Dean percer', 'Dorris liebe']
- **What it means:** Some names have lower-case surname initials (e.g. 'Dorris liebe'). One name is hyphenated without a space ('Corey-Lock').
- **Why this decision:** Casing is cosmetic but appears in reports. Fixing the first letter is safe. Splitting 'Corey-Lock' would be a guess, so it is left as is.
- **Approach:** Capitalise the first letter of any word that starts lower-case. Do not rewrite name structure.

### DQ05 — Identity anomaly: one customer name under several IDs, and orders with several customers
- **Severity:** High | **Decision:** FLAG | **Rows in issue log:** 10
- **Evidence:** names with several IDs: ['Harry Olson']; orders with several customers: ['CA-2025-121465', 'CA-2026-130494']
- **What it means:** A single customer name appears under five sequential IDs. Two orders, one year apart, contain identical lines, each line under a different one of these IDs. An order should belong to exactly one customer.
- **Why this decision:** This pattern is typical of injected or synthetic test records. The financial value is small, but it would distort customer counts and customer-level metrics. Merging the IDs would be a guess, and deleting real transactions without business confirmation would be unsafe.
- **Approach:** Keep the rows. Set dq_is_identity_anomaly = True for every row of the affected customer IDs and orders. Exclude these rows from customer-level analysis via exclude_from_customer_analysis. Raise them with the business owner.

### DQ06 — Placeholder / test customer name
- **Severity:** High | **Decision:** FLAG | **Rows in issue log:** 15
- **Evidence:** names: ['Sample Company A']; sales 4,624.57
- **What it means:** A customer is named like a test account (e.g. 'Sample Company A').
- **Why this decision:** If it is test data, it should not count as a real customer. However, its transactions look like normal sales, so deleting them would change reported revenue without evidence.
- **Approach:** Keep in financial totals, flag with dq_is_placeholder_customer, exclude from customer-level analysis, and escalate for confirmation.

### DQ07 — Product ID and Product Name are not one-to-one
- **Severity:** Medium | **Decision:** DOCUMENT | **Rows in issue log:** 667
- **Evidence:** 32 IDs with 2+ names; 17 names with 2+ IDs
- **What it means:** Some Product IDs are used for two different product names, and some names appear under two IDs. Product ID is therefore not a reliable unique product key on its own.
- **Why this decision:** We cannot know which name is 'correct'. Overwriting either would invent data. Category and sub-category remain consistent, so higher-level analysis is unaffected.
- **Approach:** No change to values. In Phase 2, build a surrogate product_key on (product_id, product_name) for product-level analysis.

### DQ08 — Copied financial values across different products in the same order
- **Severity:** Low | **Decision:** FLAG | **Rows in issue log:** 2
- **Evidence:** orders: ['CA-2023-123625']
- **What it means:** Within one order, two different products carry exactly the same sales, quantity, discount and profit, and the implied unit price does not fit one of the products.
- **Why this decision:** This suggests a manual copy-paste error, but the true values are unknown.
- **Approach:** Flag both rows with dq_is_value_copy_suspect. Keep the values.

### DQ09 — Unstable implied list price for the same product
- **Severity:** Medium | **Decision:** FLAG | **Rows in issue log:** 60
- **Evidence:** 45 products affected; max ratio to median 436x
- **What it means:** Implied list price = sales / (quantity x (1 - discount)). For most products this is stable. For some rows it differs by more than 50% from the product's median, in extreme cases by more than 100x.
- **Why this decision:** Large deviations point to pricing or entry errors, or to product-ID reuse. They matter for pricing and discount analysis, but there is no source to correct them from.
- **Approach:** Flag rows with dq_is_price_anomaly. Test the sensitivity of pricing and discount findings with and without these rows in later phases.

### DQ10 — Extreme values in sales and profit (statistical outliers)
- **Severity:** Info | **Decision:** FLAG | **Rows in issue log:** 1335
- **Evidence:** fences [-559.62, 786.34]; these rows hold 50.8% of total sales
- **What it means:** Sales and profit are highly right-skewed: a minority of lines falls beyond the 3 x IQR fences yet carries roughly half of all sales and profit. The high count itself shows a long-tailed distribution, not widespread errors.
- **Why this decision:** These are plausible large B2B or high-value transactions, not impossible values. Removing them would delete real business, including the largest losses management needs to see.
- **Approach:** Keep all rows. Flag with dq_is_sales_outlier / dq_is_profit_outlier (3 x IQR). Prefer medians and ratio-of-sums in analysis.

### DQ18 — Canadian order lines that are copies of other orders' lines
- **Severity:** High | **Decision:** FLAG | **Rows in issue log:** 101
- **Evidence:** 144 lines in clone groups; 101 non-US copies (sales 16,113.13 = 55% of Canadian sales); 43 US lines are the matching originals
- **What it means:** Order IDs end in a 6-digit sequence number. Many Canadian lines share the sequence number, customer, product and exact sales value of a line in another order: either a US order (CA copy of a US line), or another Canadian order from a different year. US orders never repeat sequence numbers among themselves.
- **Why this decision:** This is strong evidence that part of the Canadian data was generated by copying existing records. Counting the copies would double-count revenue and invent Canadian demand. We cannot prove which side is the original for CA-CA pairs, so values are not deleted.
- **Approach:** Flag the non-US rows in each clone group with dq_is_clone_copy (assumption A6: US records are the originals). Recommend reporting Canada separately or excluding it from the core analysis.

- **Why this decision:** Geography is attributed per line, so totals by city and state remain correct.
- **Approach:** No change. Attribute geography at line level, never order level.

## 8. Assumptions carried forward
- A1: `sales` is net of discount.
- A2: Canadian values use the same currency as US values.
- A3: `profit` is not adjusted for returns.
- A4: Implied list price = sales / (quantity × (1 − discount)).
- A5: Dataset years are synthetic and are referred to as 'dataset years'.
- A6: Where a Canadian line duplicates a US line, the US line is the original and the Canadian line is the copy.
